## Bedeutung für unseren Ablauf

Unsere Regeln sind: `ready-for-test` (später `ready-for-agent`), offene native Blocker verhindern den Start, höchstens ein aktiver Run und ein zugeordneter offener PR pro Repository/Issue. Ein Run darf nach geprüftem PR enden. Nach manuellem Merge kann das weiterhin offene Issue neu ausgewählt werden; kein langlebiger Inkrement-Run nötig. Der Skill entscheidet wie bisher über `Part of` versus Closing-Keyword; GitHubs tatsächlicher Issue-Zustand steuert die Wiederwahl.

Weder der Label-Ereigniszyklus von #477 noch die dauerhafte Einmal-Reservierung von #1110 erfüllt diese automatische Wiederwahl unverändert. Eine native Lösung für unsere Kombination aus Abhängigkeiten, offenen PRs und wiederholter Auswahl ist in den geprüften Beiträgen nicht belegt.

Fabros [dokumentierte API-/Cron-Automations](https://docs.fabro.sh/execution/automations) sind ein möglicher Baustein für einen eigenen kurzen Auswahl-Schritt. Das ist unsere technische Ableitung, keine in den untersuchten Threads ausgesprochene Maintainer-Best-Practice. Vor einer größeren Eigenentwicklung wäre die gezielte Frage in #759 nach vorgesehenem Consumer-Modell und Wiederwahl offener Multi-PR-Issues sinnvoll. Es wurde nichts gepostet.
